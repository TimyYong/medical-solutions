## 二、七个阶段

### 1. 全量扫描与索引

只读遍历 16481 个文件，提取路径、大小、时间、扩展名，按「厂商 / 项目 / 文档类型 / 业务域 / 知识价值分层」自动分类。产出 `全量文件清单.csv`、`files.jsonl`。

- **识别出 4248 个 macOS 残留垃圾**（`. _表格` 472 / `. _数值` 472 / `. _数据.json` 472 / `.DS_Store` 等）——这是源目录从 Mac 转存留下的资源分叉文件，占总数 26%。
- **知识价值分层**：A 层 6165 份知识型文档做全文索引；B 层 2900 份原始数据仅登记元数据；C 层 3168 份大文件/压缩包/图片只入册不解析。

### 2. 分类建档

沿用嘉和自身的 `00-目录说明 / 02-产品与方案 / 03-模板 / 08-行业资料` 体系而非推倒重来。生成 6 份厂商画像、180 份项目档案（文档构成、关键文档、子目录、时间跨度）。

- 修正两处误判：`区块链…数据共享…pdf` 被当成「数据报表」；关键文档按体积排序会让 300 MB 数据文件顶到最前 → 改为「类型明确优先 + 体积适中优先」。

### 3. 全文索引

`docx / xlsx / pptx / pdf / doc / xls / ppt / txt / md` 多进程并行提取，写入 SQLite FTS5。

- **中文分词是最大障碍**：SQLite 默认 `unicode61` 切不开中文，改用 **trigram** 分词器，支持任意子串匹配。
- **老式 **`.doc`** 抽出来是乱码**（Word 97 二进制压缩），用「CJK 占比高但常用字占比低」判据清掉 169 份，正文从 8308 修正为 8139 份有效。

### 4. 检索验收（这一步证明库原本不合格）

设计 14 个真实业务问题实测，发现并修掉三个缺陷：

| 缺陷 | 现象 | 修法 |
| --- | --- | --- |
| 2 字关键词让整条查询归零 | trigram 只索引 ≥3 字串，「芜湖」「控费」「投标」「接口」塞进 FTS 的 AND 表达式后直接失败，**14 题中 4 题返回 0 条** | ≥3 字走 FTS，2 字词走 SQL LIKE |
| 周报霸榜 | bm25 偏爱短文档，几十份「售前工作周报.xlsx」把真方案挤出候选集前 200 名 | 取 300 条候选 → 按类型限额（过程管理 ≤3）→ 再按位次重排 |
| 同一文档多版本占满结果 | 一份 PPT 在三个目录各存一份，一次搜索占掉前三 | 文件名归一化折叠，显示「另有 N 个版本」 |

**教训：加权排序必须让相关性说话，类型只能当裁判不能当选手。** 曾用类型权重硬压，结果把宁夏人民医院的方案排到了「301医院 样本库」第一位。

残留 1 题落空是**内容缺口而非检索问题**：绩效考核域 73 份文档里只有 9 份方案，其余是指标模板与内部制度——库里本就没有成型国考方案。

### 5. 扫描件 OCR

对 925 份无文本文件中的高价值子集（招投标 / 合同协议 / 资质证照 / 方案设计 / 政策标准 / 实施验收 / 需求调研）做识别：处理 228 份 / 1183 页，**成功 192 份，回写 58.7 万字，乱码率 0**。

| 类型 | 处理 | 成功 | 回写字数 |
| --- | --- | --- | --- |
| 资质证照 | 68 | 63 | 14.5 万 |
| 合同协议 | 55 | 52 | 21.1 万 |
| 招投标 | 30 | 19 | 10.3 万 |
| 方案设计 | 27 | 19 | 6.4 万 |
| 政策标准 / 实施验收 / 需求调研 | 48 | 39 | 6.4 万 |

四个坑：

1. **onnxruntime 1.32 在本机导入即段错误**（RC=139），降到 **1.20.1** 才正常；原装 `rapidocr-onnxruntime 1.2.3` 不支持 Python 3.13，换新包名 `rapidocr`；官方源慢到超时，走阿里云镜像。
2. **没有 PDF 渲染库也能 OCR**——用 `pypdf` 直接取扫描页内嵌图，抽样 29 份可取图率 100%，省掉 pymupdf / poppler。
3. **默认线程数让并行变成负优化**：`intra_op_num_threads=-1` 占满 22 核，4 进程互相抢，单页从 4 秒退化到 15 秒。最终定 4 进程 × 5 线程 + 检测长边压到 1280（耗时减半，识别字数只差 2 字）。
4. **后台任务运行时做基准测试，数据全是失真的**——曾得出「并行无收益」的错误结论。

### 6. 压缩包补录

320 个压缩包（zip 163 / rar 155 / 7z 2）**读取成功率 100%**，5826 个包内文件名全部入索引。

- **关键突破**：本机没装 7-Zip / unrar，但 Windows 自带 `C:\Windows\System32\tar.exe`（bsdtar，基于 libarchive）能只读解析 rar。
- 中文名在旧式 RAR 里是 GBK 字节，bsdtar 直接输出乱码，按 `utf-8 → gbk → gb18030` 依次还原后完全正确。
- 包内清单以 `[压缩包] 包名　内含 N 个文件` 开头，一眼看出是哪个包。

### 7. 清理瘦身

经确认后执行，**移动而非删除**：

| 类型 | 数量 | 体积 |
| --- | --- | --- |
| 系统垃圾（AppleDouble 4144 / Word 临时锁 69 / .DS\_Store 17 / WeDrive 15 / 缩略图 3） | 4248 | 16.2 MB |
| 同目录误复制（`xx.pdf` 与 `xx(1).pdf` 并存） | 33 | 27.9 MB |
| 合计 | **4281** | **44.1 MB** |

逐条校验：台账 4281 条全部 `MOVED`，源目录残留 0 条，隔离区缺失 0 条。

**没有全清重复文件的理由**：216 组「重复」里大部分是同一份文件在不同项目目录各存一份（如《芜湖全民健康信息平台汇报PPT》同时在项目目录与文档目录）。这不是误复制，是各目录的自包含；删掉它，那个目录就不再能独立打开。因此规则收窄为「只清同一目录内多出来的副本」，剩 291 份跨目录重复保留原状。

## 六、这一轮最值钱的三条经验

1. **库建好不等于库能用。** 检索验收一做暴露 3 个致命缺陷，其中「2 字词查询归零」让 4/14 的题直接无结果——如果不测，这套库上线就是废的。
2. **分类不能只看文件名。** 70% 落「其他」时靠正文关键词重判才救回，此后每加一层文本（OCR、压缩包清单）都要回头重判一次。
3. **动用户文件之前先算清代价。** 重复文件清单写着 401 MB 冗余，看着很诱人，实际拆开发现大半是合理的目录自包含，真按清单删会破坏项目目录的完整性。
